# Cloud sessions: how my setup reaches them

*How a Claude Code cloud session (phone, web, or Cloud in the desktop app) gets my global rules, modes, the brain skill, `brain-search`, and brain index rebuilds, and how to turn it on for another repo. Set up and tested on claude-assistant 2026-10-14.*

## How it works (checked 2026-10-14)
- A cloud session runs on a fresh clone of the one repo I pick. It doesn't have my PC's `~/.claude`, and hooks from `~/.claude/settings.json` don't run there; hooks from the repo's own `.claude/settings.json` do.
- A cloud session can only reach the GitHub repos picked when it starts. **`dot-claude` is public**, so anyone can clone it with a plain URL, without logging in. Everything in it, including its history, is readable by anyone (`CLAUDE.md`, the skills, this brain), so no secrets go in it.

- **The setup script clones dot-claude, nothing else (decided 2026-10-26, later the same day):** the environment's setup script is one line, `git clone https://github.com/serina-sketch/dot-claude.git ~/.claude`. `cloud.sh` and its hooks were deleted from claude-assistant. Why: I no longer rely on cloud environment tricks, and `cloud.sh` had grown too complicated while still failing. The frozen copy is no longer a problem, because `~/.claude`'s own start hook (`git_sync.py`) resets it to GitHub's `master` at every chat start. dot-claude doesn't need to be attached any more.
- **What the docs say (checked 2026-10-26, [cloud environments](https://code.claude.com/docs/en/cloud-environments)):** the setup script runs before Claude Code starts, and its result is saved as a snapshot and reused by later sessions (that's the caching). SessionStart hooks run after Claude Code has started, so a hook that fills `~/.claude` comes too late for that chat's global `CLAUDE.md` and skills. A session with several repos attached doesn't run any repo's `.claude/settings.json` hooks at all. That's why the failed test below never ran `cloud.sh sync`: dot-claude was attached too. The docs suggest the setup script for writing `~/.claude/CLAUDE.md`.
- **`~/.claude`'s own hooks do run on cloud once the folder exists (seen 2026-10-26):** the docs say user settings don't reach the cloud, which only means they aren't copied from the PC. When `~/.claude/settings.json` is on disk in the container, its hooks run: `git_sync.py` pulled 2 commits into `~/.claude` at the start of a chat on 2026-10-26.
- **Leftover catch:** the global `CLAUDE.md` is read before the start hook pulls, so a chat's global rules can be a commit or two behind until the next chat.
- **Order at container start (seen 2026-10-26 in the cloud UI):** the container is set up, then the attached repos are cloned (into `/home/user/<repo>`), then the setup script runs, then Claude Code starts. So a repo attached to the session is already on disk before any hook runs.

- **Writing to dot-claude from a cloud session (checked 2026-10-15):** when a change is needed, Claude attaches `dot-claude` partway through the session with write access (the `add_repo` tool), clones it to `/home/user/dot-claude`, commits and pushes there, then pulls into `~/.claude` (~~`bash .claude/cloud.sh sync`~~ `git -C ~/.claude pull` since 2026-10-26) to get the new version. Tested on 2026-10-15 from claude-assistant on the phone: a push dry-run went through. The attachment only lasts for that session.
- **Any of my repos, partway through a session (checked 2026-10-15):** the same `add_repo` attach works for every repo, not only dot-claude. Tested by moving mimitabi's `claude-tools/` into its `.brain/tools/` from a claude-assistant session on the phone: attached with write access, cloned to `/home/user/mimitabi`, committed and pushed to master. I decided this is how Claude reaches another repo on cloud (2026-10-15).
- **Tested 2026-10-22 on a new claude-assistant chat (all OK):** `~/.claude/CLAUDE.md` loaded, `brain-search` was listed, the session-start sync printed no errors, and `CLAUDE_CODE_REMOTE` was `true`.

## If something breaks
- No global rules or `brain-search`: check the environment's setup script still has the clone line, and that `~/.claude/.git` exists. ~~read `/tmp/cloud-sync.log`, then run `bash .claude/cloud.sh sync`~~ (Replaced 2026-10-26.) If `~/.claude` is empty, run the clone line by hand; the rules load only in the next chat after that.
- Indexes not rebuilding: check that `~/.claude/settings.json` has the hooks and that `~/.claude/skills/brain/brain_index.py` exists.
- Changes to the setup script take effect in the next new session (it also rebuilds the cache).
- **The cloud edits its own `~/.claude` (seen 2026-10-26):** the cloud copy's `settings.json` had `"model": "opus"` changed to `"opus[1m]"`, and Claude Code had added a built-in `skills/session-start-hook/` folder (untracked, harmless). ~~Since 2026-10-26 the sync sets such edits aside and keeps GitHub's version if they clash.~~ Since later on 2026-10-26 the sync simply resets the cloud copy to GitHub's `master` (`design/git-sync.md`).
