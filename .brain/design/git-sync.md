Why: I now work in about five repos at once (five folders in one VS Code workspace), on the PC and in cloud sessions at the same time, and the copies drifted out of sync. Too much to track by hand.

- **Only at session start, only the workspace folders (decided and built 2026-10-15):** the sync runs once when a chat starts, and covers only the folders in the repo's `.code-workspace` file plus `~/.claude`, not every repo in the serina-sketch folder. No sync before commits or after pushes. Why: the full sweep took about 11 seconds before every commit, and claude-assistant commits after every write. The problem I actually want solved is a PC chat starting on a stale copy after I changed something in the cloud (or the other way round). Cloud sessions already start from a fresh clone, and git itself refuses a push when `master` has moved, so the pull at the start is the only part that's needed.
- **Always one line (2026-10-15):** the sync always prints a line at session start, even when nothing was pulled ("Git sync: N repo(s) up to date (…)"). Why: a quiet run looked the same as no run, so I couldn't tell whether the hook had fired.
- **Long sessions (2026-10-15):** two sessions writing to the same repo at once can still collide, and no tool fixes that. I'm moving away from long chat sessions anyway: the brain carries the context, so a new chat picks up where the last one stopped.

## Cloud sessions skip the local master (decided 2026-10-19)
- **Decided 2026-10-19:** in cloud sessions, Claude never uses the container's local `master` branch. After each commit it pushes the session branch straight to GitHub's `master` (`git push origin HEAD:master`); if the push is rejected, it merges `origin/master` into the session branch and pushes again. The rule is in the global `CLAUDE.md`, under "Git: always master". I chose only the rule, not a script that also resets the local `master`.
- **Why:** the local `master` in a cloud container is a frozen copy. In claude-assistant's cloud environment it was created on 2026-10-14 at 22:36 UTC, when the environment was first set up, and it was 202 commits behind on 2026-10-19. Each new session only downloads GitHub's latest `master` into the session branch; nothing ever updates the local one.
- **What the 2026-10-16 error really was (found 2026-10-19):** the "refusing to merge unrelated histories" error was not dot-claude history leaking into claude-assistant. The frozen local `master` is real claude-assistant history (its last commit is a claude-assistant commit). Cloud clones only download the last 50 commits, so git couldn't see that the old `master` and the new one connect, and called them unrelated. After downloading more history (`git fetch --deepen=200 origin master`), the old `master` showed up as a plain ancestor of GitHub's.
- ~~**The sync script fixes it too (decided and built 2026-10-19):** in cloud sessions only, `git_sync.py` resets each repo's local `master` to GitHub's at chat start (when `master` isn't the branch in use). Why: the written rule alone depends on every chat remembering it, and every new cloud environment freezes its own old `master`, so the problem kept coming back in each repo. The rule stays as a backup.~~ Replaced 2026-10-26 (see "Simpler sync" below).
- ~~**Cloud syncs every repo side by side (decided and built 2026-10-19):** in cloud sessions, `git_sync.py` also covers every repo of mine in the same parent folder (`/home/user/<repo>`), where attached repos are cloned. Why: a chat can open in that parent folder instead of inside a repo, and then only `~/.claude` got synced. The PC keeps the workspace-file rule.~~ Replaced 2026-10-26 (see "Simpler sync" below).
- **The cloud git rule moved (2026-10-19):** it now lives under "Cloud sessions" in the global `CLAUDE.md`, with a pointer left under "Git: always master". Why: it only applies to cloud, and that section already exists for cloud rules.

- ~~**The cloud's own edits to `~/.claude` never block the sync (decided and built 2026-10-26):**~~ Replaced later on 2026-10-26 (see "Simpler sync" below). in cloud sessions only, for `~/.claude` only, `git_sync.py` sets the copy's local edits aside before pulling GitHub's `master`, then puts them back. If they clash, GitHub's version is kept and the sync line says so, instead of stopping. Why: on 2026-10-26 a cloud chat started blocked. The cloud had changed `"model": "opus"` to `"opus[1m]"` in that copy's `settings.json`, and my PC commits had changed the same line to `"sonnet"`, so the merge was aborted. I never edit that copy, so nothing in it is mine to lose. Local commits there would still stop the sync as before.

- **How `cloud.sh sync` fills `~/.claude` (decided and built 2026-10-26):** when `~/.claude` has no `.git`, it copies the `dot-claude` clone that sits next to the project (`/home/user/dot-claude`, there when `dot-claude` is attached to the session) and puts it on `master`; only without that copy does it clone from GitHub. Then, every time, it fetches GitHub's `master` and resets `~/.claude` to it exactly (instead of `pull --ff-only`, which gave up silently when the cloud had edited its copy). It logs each step to `/tmp/cloud-sync.log` and prints one "Cloud sync:" line. Why: the setup script that used to fill `~/.claude` is gone, the start-time GitHub clone failed in the first test without saying why, and attached repos are already on disk before the hooks run. Catch: without `dot-claude` attached, it still depends on the GitHub clone. ~~(whole entry)~~ Replaced later on 2026-10-26: `cloud.sh` is deleted.

## Simpler sync (decided and built 2026-10-26)
- **What I decided:** delete `cloud.sh` from claude-assistant, and keep `git_sync.py` for the PC with its cloud extras taken out. The environment's setup script clones `dot-claude` into `~/.claude` (`knowledge/cloud-setup.md`). Why: there was too much that didn't work, and the setup had grown too complicated.
- **What `git_sync.py` does now:** the same on the PC and on cloud: it pulls the current repo, the folders in its `.code-workspace` file, and `~/.claude`. One cloud difference only: `~/.claude` on cloud is reset to GitHub's `master` instead of merged, since nothing in that copy is mine to keep and the cloud edits its `settings.json` by itself.
- **Taken out:** resetting each repo's frozen local `master` (the "never use the local master" rule in the global `CLAUDE.md` is enough), the scan of every repo next to the current one, and setting the cloud's edits aside before the pull.
